# Phase 3 — Database Schema Design

> **Note:** This schema was originally designed for Firebase Firestore and
> has been revised for **SQLite**, per instruction to switch database
> technology. The required fields and business logic are unchanged — only
> the storage engine, data types, and structural details below reflect
> SQLite instead of Firestore.

## 3.1 Database Purpose

The database will store business sales and transaction data required by
the Conversational Analytics Platform.

The stored data must support the 17 approved use cases defined in Phase 2,
including sales analysis, profit analysis, category and regional analysis,
time-based trends, customer order lookup, and sales-profit relationship
analysis.

The database is implemented using **SQLite**, a lightweight, file-based
relational database. The initial design uses a single flat table and does
not require separate customer, product, or inventory tables.

---

## 3.2 Schema Design Principles

The schema follows these principles:

* One SQLite table will store the business transaction data.
* One row will represent one order or transaction record.
* The design uses a flat structure to keep data retrieval simple for the
  initial project scope.
* Fields are based on the approved Phase 2 requirements.
* No additional fields are included in the initial schema.
* Field names use consistent `snake_case` naming.
* The schema must support filtering, grouping, sorting, ranking,
  aggregation, time-based analysis, record lookup, and numerical
  relationship analysis — all of which SQL supports natively.
* Indexes are added on columns that are frequently filtered or grouped by,
  to keep queries fast as the table grows.

---

## 3.3 Field Definitions

The schema contains the following 12 fields.

| Field Name      | SQLite Type | Required | Description                                         | Example          |
| --------------- | ----------- | -------- | ---------------------------------------------------- | ---------------- |
| `order_id`      | TEXT        | Yes      | Unique identifier for an order or transaction.      | `"CA-2024-1001"` |
| `order_date`    | TEXT (ISO 8601 date) | Yes | Date when the order was recorded. Stored as `YYYY-MM-DD`; SQLite has no native date type. | `"2024-03-15"`   |
| `product`       | TEXT        | Yes      | Name of the product associated with the order.      | `"Office Chair"` |
| `category`      | TEXT        | Yes      | Business category of the product.                   | `"Furniture"`    |
| `city`          | TEXT        | Yes      | City associated with the sales record.              | `"New York"`     |
| `region`        | TEXT        | Yes      | Geographic region associated with the sales record. | `"East"`         |
| `sales`         | REAL        | Yes      | Total sales amount for the record.                  | `1250.50`        |
| `quantity`      | INTEGER     | Yes      | Number of units sold.                               | `5`               |
| `unit_price`    | REAL        | Yes      | Price of one unit of the product (derived: sales ÷ quantity). | `250.10`   |
| `discount`      | REAL        | Yes      | Discount applied to the order or transaction.       | `0.10`           |
| `profit`        | REAL        | Yes      | Profit generated by the record. Can be negative.    | `180.25`         |
| `customer_name` | TEXT        | Yes      | Name of the customer associated with the order.     | `"John Smith"`   |

**Note on `order_id`:** the raw dataset can contain multiple rows sharing
the same `Order ID` (an order with several product line items). Because of
this, `order_id` is kept as a regular indexed column rather than the
primary key — a separate auto-increment `id` column is used as the actual
primary key instead (see Section 3.5).

## 3.4 Field-Level Validation Rules

| Field           | Validation Rule                                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| `order_id`      | Required, must not be empty (`NOT NULL`).                                                                          |
| `order_date`    | Required, must be a valid ISO 8601 date string (`NOT NULL`).                                                        |
| `product`       | Required, must not be empty (`NOT NULL`).                                                                          |
| `category`      | Required, must not be empty (`NOT NULL`).                                                                          |
| `city`          | Required, must not be empty (`NOT NULL`).                                                                          |
| `region`        | Required, must not be empty (`NOT NULL`).                                                                          |
| `sales`         | Required, must be a valid numeric value (`NOT NULL`).                                                              |
| `quantity`      | Required, must be a valid integer greater than zero (`NOT NULL`, `CHECK (quantity > 0)`).                          |
| `unit_price`    | Required, must be numeric and greater than or equal to zero (`NOT NULL`, `CHECK (unit_price >= 0)`).                |
| `discount`      | Required, must be a valid numeric value (`NOT NULL`).                                                              |
| `profit`        | Required, must be numeric. Negative values are allowed because a transaction may result in a loss (`NOT NULL`).    |
| `customer_name` | Required, must not be empty (`NOT NULL`).                                                                          |

SQLite's `CHECK` constraints enforce the `quantity > 0` and
`unit_price >= 0` rules directly at the database level, in addition to
validation already performed by the cleaning script in Phase 6.

## 3.5 Table Structure (SQLite)

```sql
CREATE TABLE IF NOT EXISTS sales (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id      TEXT    NOT NULL,
    order_date    TEXT    NOT NULL,
    product       TEXT    NOT NULL,
    category      TEXT    NOT NULL,
    city          TEXT    NOT NULL,
    region        TEXT    NOT NULL,
    sales         REAL    NOT NULL,
    quantity      INTEGER NOT NULL CHECK (quantity > 0),
    unit_price    REAL    NOT NULL CHECK (unit_price >= 0),
    discount      REAL    NOT NULL,
    profit        REAL    NOT NULL,
    customer_name TEXT    NOT NULL
);

-- Indexes on columns used frequently for filtering/grouping in the
-- 17 approved use cases (city, category, region, date-based trends).
CREATE INDEX IF NOT EXISTS idx_sales_city ON sales (city);
CREATE INDEX IF NOT EXISTS idx_sales_category ON sales (category);
CREATE INDEX IF NOT EXISTS idx_sales_region ON sales (region);
CREATE INDEX IF NOT EXISTS idx_sales_order_date ON sales (order_date);
CREATE INDEX IF NOT EXISTS idx_sales_customer_name ON sales (customer_name);
```

An auto-incrementing `id` column is used as the primary key, since one
order can contain multiple product line items and therefore multiple rows
can share the same `order_id`.

## 3.7 Query Requirements

The database must support the approved Phase 2 use cases through
filtering, grouping, sorting, aggregation, and date-based queries — all of
which map directly onto standard SQL clauses.

| Requirement           | Example                        | SQL Concept                              |
| ---------------------- | -------------------------------- | ------------------------------------------ |
| Aggregation            | Total sales, total profit        | `SUM()`                                    |
| Filtering              | Sales for a specific city        | `WHERE city = ?`                           |
| Grouping               | Sales by category or region      | `GROUP BY category`                        |
| Sorting                | Products by sales                 | `ORDER BY sales DESC`                      |
| Ranking                | Top 5 products by sales           | `ORDER BY ... LIMIT 5`                     |
| Date filtering         | Sales within a date range         | `WHERE order_date BETWEEN ? AND ?`         |
| Time grouping          | Monthly sales                     | `GROUP BY strftime('%Y-%m', order_date)`   |
| Customer lookup        | Orders for a specific customer    | `WHERE customer_name = ?`                  |
| Relationship analysis  | Sales vs profit                   | `SELECT sales, profit FROM sales` (scatter) |

The AI engine will identify the required fields and operations from the
user's question. The backend will then translate this structured
information into a parameterized SQL query and execute it against SQLite.

## 3.9 Final Schema

The final SQLite schema contains 12 business fields plus an internal
auto-increment `id`:

`id`, `order_id`, `order_date`, `product`, `category`, `city`, `region`,
`sales`, `quantity`, `unit_price`, `discount`, `profit`, `customer_name`

The data is stored in a single `sales` table, with one row representing
one transaction/line-item record. Indexes are defined on `city`,
`category`, `region`, `order_date`, and `customer_name`.
