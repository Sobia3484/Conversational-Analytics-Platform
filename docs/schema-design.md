# Phase 3 — Database Schema Design

## 3.1 Database Purpose

The database will store business sales and transaction data required by the Conversational Analytics Platform.

The stored data must support the 17 approved use cases defined in Phase 2, including sales analysis, profit analysis, category and regional analysis, time-based trends, customer order lookup, and sales-profit relationship analysis.

The database schema is designed for SQLite using a single `sales` table.

---

## 3.2 Schema Design Principles

- One SQLite table will store the business transaction data.
- One row will represent one sales transaction/order-line record.
- The design uses a flat structure for simple querying.
- Fields are based on the approved Phase 2 requirements.
- No additional fields are included in the initial schema.
- Field names use consistent `snake_case` naming.
- The schema must support filtering, grouping, sorting, ranking, aggregation, date-based analysis, record lookup, and numerical relationship analysis.

---

## 3.3 Field Definitions

The initial schema contains 12 fields.

| Field Name | SQLite Type | Required | Description |
|---|---|---|---|
| `order_id` | TEXT | Yes | Order or transaction identifier. |
| `order_date` | TEXT | Yes | Order date stored in ISO format. |
| `product` | TEXT | Yes | Product name. |
| `category` | TEXT | Yes | Product category. |
| `city` | TEXT | Yes | City associated with the sales record. |
| `region` | TEXT | Yes | Geographic region. |
| `sales` | REAL | Yes | Sales amount for the record. |
| `quantity` | INTEGER | Yes | Number of units sold. |
| `unit_price` | REAL | Yes | Sales divided by quantity. |
| `discount` | REAL | Yes | Discount applied to the transaction. |
| `profit` | REAL | Yes | Profit generated by the record. |
| `customer_name` | TEXT | Yes | Customer name. |

---

## 3.4 Field-Level Validation Rules

| Field | Validation Rule |
|---|---|
| `order_id` | Required and must not be empty. |
| `order_date` | Required and stored as a valid ISO date. |
| `product` | Required and must not be empty. |
| `category` | Required and must not be empty. |
| `city` | Required and must not be empty. |
| `region` | Required and must not be empty. |
| `sales` | Required and must be numeric. |
| `quantity` | Required and greater than zero. |
| `unit_price` | Required and greater than or equal to zero. |
| `discount` | Required and must be numeric. |
| `profit` | Required and must be numeric. Negative values are allowed. |
| `customer_name` | Required and must not be empty. |

## 3.6 Query Requirements

The database must support the approved Phase 2 use cases through filtering, grouping, sorting, aggregation, and date-based queries.

| Requirement | Example |
|---|---|
| Aggregation | Total sales, total profit |
| Filtering | Sales for a specific city |
| Grouping | Sales by category or region |
| Sorting | Products by sales |
| Ranking | Top 5 products by sales |
| Date filtering | Sales within a date range |
| Time grouping | Monthly sales |
| Customer lookup | Orders for a specific customer |
| Relationship analysis | Sales vs profit |

The AI engine will identify the required fields and operations from the user's question. The backend will then use this structured information to query and process the actual data stored in SQLite.

## 3.8 Final Schema

The final SQLite database contains one table named `sales` with 12 columns:

`order_id`, `order_date`, `product`, `category`, `city`, `region`, `sales`, `quantity`, `unit_price`, `discount`, `profit`, `customer_name`

### SQLite Table

```sql
CREATE TABLE sales (
    order_id TEXT NOT NULL,
    order_date TEXT NOT NULL,
    product TEXT NOT NULL,
    category TEXT NOT NULL,
    city TEXT NOT NULL,
    region TEXT NOT NULL,
    sales REAL NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price REAL NOT NULL,
    discount REAL NOT NULL,
    profit REAL NOT NULL,
    customer_name TEXT NOT NULL
);
